## Промт

```
Репозиторий: ~/work/agent-skills. Задача — исправить дефект рантайма MB3, из-за
которого DA-гейты молча отключаются на задачах с числовым complexityTier.

СИМПТОМ (наблюдался в проекте ~/work/ai-editor-3, TASK-022):
PostToolUse-хук отклонил валидный вердикт mb3-critic с сообщением
«[MB3 DA Gate NOT APPLICABLE — gate_tier_excluded] CREATIVE for TASK-022 (4):
the gate requires minTier 3 — this task is below it». Утверждение ложно:
4 >= 3. Полноценный вердикт REVISE с 10 находками (одна HIGH) был потерян
для рантайма; гейт-история задачи осталась пустой, хотя ревью состоялось.
Воспроизвелось дважды подряд.

КОРЕНЬ (подтверждён прогоном, не гипотеза):
plugins/_shared/runtime/da-enforcement.ts:212

  export function parseTierLevel(complexityTier: string): number {
    const match = String(complexityTier || "").match(/T(\d)/);
    return match ? Number(match[1]) : 0;
  }

Регулярка требует литерал 'T'. В tasks-registry.jsonl у TASK-022 хранится
complexityTier=4 — голое ЧИСЛО, а не строка 'T4'. String(4)='4', совпадения
нет, функция возвращает 0.

Дальше plugins/_shared/runtime/gate-policy-resolver.ts:427:

  if (parseTierLevel(tier) < effective.minTier) {
    return { rule: null, cause: "gate_tier_excluded", minTier: effective.minTier };
  }

0 < 3 → gate_tier_excluded. Ровно то сообщение, что видел оператор.

Проверочный прогон (bun -e), фактический вывод:
  parseTierLevel(4)              -> 0
  parseTierLevel("4")            -> 0
  parseTierLevel("T4")           -> 4
  parseTierLevel("T4:standard")  -> 4
  parseTierLevel("T3:moderate")  -> 3

МАСШТАБ — ЭТО НЕ КОСМЕТИКА:
0 ниже minTier ЛЮБОГО гейта. Значит у задачи с числовым tier молча отключены
ВСЕ DA-гейты во ВСЕХ фазах (CREATIVE, PLAN, TECH_SPEC, IMPLEMENT, QA,
CODE_REVIEW), а не только тот, на котором это заметили. mb3_task status при
этом честно показывает gateMode:"strict" и required:true по каждой фазе, то
есть задача ВЫГЛЯДИТ полностью гейтованной, а на деле не гейтована вовсе.
Отказ тихий и маскируется под штатное tier-исключение. Это дыра в
gate-honesty: незакрытая работа может пройти как закрытая.

ДЕФЕКТА ДВА, чинить оба:

(1) ЧТЕНИЕ. parseTierLevel не принимает числовую форму и деградирует в 0.
    Ноль — худшее из возможных значений по умолчанию: он не «неизвестно», он
    «ниже всех порогов», то есть неразобранный tier беззвучно снимает защиту.
    Продублирована дословно в двух местах:
      - plugins/_shared/runtime/da-enforcement.ts:212
      - plugins/_shared/runtime/mcp-server/engine/da-review/da-helpers-core.ts:58
    Обе копии обязаны быть исправлены. Предпочтительно свести к одному
    источнику, если это не ломает границы модулей — но сначала убедись, что
    дублирование не намеренное (проверь импорты и историю).

(2) ЗАПИСЬ. mb3_task create получил tier:4 числом и записал его в реестр без
    канонизации в 'T4:standard'. В tasks-registry.jsonl проекта ai-editor-3
    из 24 записей с complexityTier числовая ровно ОДНА (TASK-022), остальные —
    'T2', 'T3', 'T4', 'T3:moderate', 'T2:quick'. То есть create допускает
    второе представление того же поля. Нормализуй на записи, чтобы реестр
    держал одну каноническую форму.

ЧЕГО НЕ ДЕЛАТЬ:
- Не «расширяй регулярку» вслепую. parseTierLevel вызывается и для tier
  задачи, и для minTier из манифеста (gate-policy-resolver.ts:223 —
  parseTierLevel(entry.minTier)). Любое изменение обязано сохранить текущее
  поведение на строках 'T<N>' и 'T<N>:label'.
- Не трогай порядок проверок в projectRuleWithCause
  (absent → not-required → tier-excluded). Он помечен в коде как
  load-bearing и закреплён тестом
  plugins/__tests__/task639-gate-absence-cause.test.ts. Переупорядочивание
  переклассифицирует required:false как gate_tier_excluded.
- Не чини это правкой одной строки без тестов: дефект невидим в проде именно
  потому, что тихий.

ДОПОЛНИТЕЛЬНО ПРОВЕРЬ (нашёл попутно, подтверди или отвергни фактами):
- /T(\d)/ ловит один разряд: 'T10' разберётся как 1. Актуально, если tier
  когда-либо перевалит за 9.
- Регулярка не заякорена: строка вида 'NOT4ATIER' даст совпадение.
- Есть ли ещё места, где неразобранное/отсутствующее значение деградирует в
  0 и тем самым СНИМАЕТ ограничение вместо того, чтобы его сохранить. Это
  класс дефекта, а не единичный случай — поищи по тому же шаблону
  (`? Number(...) : 0`).

ТРЕБОВАНИЯ К ТЕСТАМ (без них задачу не закрывать):
- parseTierLevel: числовой вход 4, строковый '4', 'T4', 'T4:standard',
  'T3:moderate', плюс мусор/undefined/null. Обе копии функции.
- projectRuleWithCause: задача с tier=4 (ЧИСЛОМ) и гейтом minTier=3 →
  гейт ПРИМЕНИМ, cause отсутствует. Это тест-регрессия ровно на этот баг,
  он обязан краснеть на текущем HEAD.
- Порядок absent → not-required → tier-excluded не сломан (существующий
  task639-gate-absence-cause.test.ts должен остаться зелёным).
- Путь записи: create с tier:4 кладёт в реестр каноническую строку.

МИГРАЦИЯ:
Реши и обоснуй, что делать с уже записанной числовой записью TASK-022 в
~/work/ai-editor-3/memory-bank/system/tasks-registry.jsonl. Варианты —
одноразовая нормализация, ленивая нормализация при чтении, или оба.
Учти, что реестр append-only JSONL: переписывание истории может быть
неприемлемо, тогда правильный ответ — терпимость на чтении.

ПРОВЕРКА:
Запусти тесты пакета и убедись, что новый регрессионный тест краснеет ДО
правки и зеленеет ПОСЛЕ. Зелёный прогон без предварительного красного не

ЛОВУШКА, СПЕЦИФИЧНАЯ ДЛЯ ЭТОЙ ЗАДАЧИ:
Если будешь вести работу через MB3 в agent-skills — не создавай себе задачу
```

## Открытый вопрос, который я решать не стал

Числовой `tier` пришёл из моего же вызова `mb3_task create` с `tier: 4`. Схема MCP-инструмента описывает параметр как `tier?` без указания формы. Стоит решить, что считать контрактом: принимать оба вида и канонизировать (мягко), либо отвергать числовой с внятной ошибкой (жёстко). Первое согласуется с CD-65 «graceful recovery over rigid reject», второе быстрее ловит ошибку на входе. Я склоняюсь к первому плюс нормализация на записи — но это решение владельца рантайма.
